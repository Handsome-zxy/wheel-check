# wheel-check 决策记录（rulings）

本文件是这次构建留下的**裁决台账**：每一条都是真正做过的决定，带一行理由和"如果判断错了要付什么代价"。
它是**入库的**记录——README 与设计文档都指向这里。

> 原始会话台账（`.superpowers/sdd/wheel-check/progress.md`，含逐任务的派发、复核与已知次要点的流水）**不入库**，
> 是本次构建的草稿纸：它按时间顺序写、包含大量过程噪声。本文件是从它提炼出的结论，被删掉的只有过程细节，
> 没有结论。设计文档 §13 是实现与 spec 的**偏差**记录，本文件是**裁决**记录，两者互补。

格式：**决策 → 理由（一行）→ 代价（若判断错了）**。带 ★ 的是本项目最不能让步的几条。

## 1. 调用形状与退出码

| # | 决策 | 理由 | 代价（若判断错了） |
|---|---|---|---|
| 1.1 ★ | **解析期错误一律退出码 3**：`_ArgParser` 覆盖 argparse 的默认 `sys.exit(2)` | `2` 在本项目里是 `degraded`——一个畸形调用绝不能被读成一次检索失败（"没查成"和"参数写错了"是两件事） | 删一个类 + 一个 try/except；但在此之前，任何 `--source nope` 都会被上报成检索降级 |
| 1.2 ★ | `validate_terms()` 在 `main()` 里、**在** `search_envelope()` 之前跑 | 空 `--terms` 必须在发出任何请求之前就变成退出码 3，而不是变成"0 结果的 ok 信封" | 一个空词表会伪装成"确实没有先例"——本项目最坏的失败 |
| 1.3 | `main()` 把**清洗过的词表**交给检索层，且**绝不二次校验** | `validate_terms` 按 `\|` 切分，对列表再跑一次会抛 `AttributeError` | 一行多余调用就能让 CLI 崩在 `AttributeError` 上 |
| 1.4 | `--limit` 两条路径**刻意不对称**：CLI 超范围 → 退出码 3；程序化调用 → 静默夹到 1..100 | CLI 上那是"调用写错了"；程序化调用是边界保护，且 GitHub/HN 会静默归一化或直接拒绝越界值 | 一条路径会发出必然被拒的请求；不对称已写进 README 与 §13.7 |
| 1.5 | `repo <owner/name>` 的格式校验在**发请求之前**，不合法即退出码 3 | `repo owner/typo` 是"这个名字不对"，不是"网络/API 不高兴" | 用户被送去查网络，而真正的问题是名字打错了 |
| 1.6 | **`bad-args` 不是 `reason` 的取值**，只由退出码 3 表达（spec §4.3 的枚举已据此删掉它） | 参数错误发生在信封产生之前；把退出码混进字段枚举会让机读方去找一个永不出现的值 | 机读方可能把"调用写错了"读成"检索没成功"（详见设计文档 §13.9） |

## 2. 请求预算、重试与凭据

| # | 决策 | 理由 | 代价（若判断错了） |
|---|---|---|---|
| 2.1 ★ | **403/429 的重试放在 fetch 包装器里**（`_retrying_fetch`），不是放在档位循环外面 | 重试属于**这次检索**而不属于某一档：一个持续 403 必须只花 2 次请求（原始 + 重试）就抛出，循环绝不带着已经拒绝我们的 API 继续走放宽档 | 一次检索最多花到 6 次请求；放在包装器里则上限是 **3 个档位请求 + 1 次重试 = 4**（本行原先同时写着 6 与 4，已订正为单一的最坏情况 **4**，即 `test_one_retry_per_search_caps_requests_at_three_tiers_plus_one` 证明的那个数） |
| 2.2 | 退避固定 **1.0 秒**，而 GitHub 的搜索窗口是 **60 秒** | brief 指定值；且真正的补救是设 `GITHUB_TOKEN`，不是重试 | 真遇到配额耗尽时，这一次重试基本只是再确认一遍 403，还多花掉 1 次/分钟（已记为已知限制） |
| 2.3 | **5xx 保持 `timeout`**，不新增 `server-error` 取值 | 5xx 的补救动作与 `timeout` 完全相同（稍后重试），而加新取值属于改 spec | 500 的措辞把人往"超时"上引（措辞不精确，行为一致；§13.5） |
| 2.4 | `GITHUB_TOKEN`（回退 `GH_TOKEN`）以 `Authorization: Bearer` **只发给 `api.github.com`** | Algolia 与 HF 是无密钥第三方，GitHub 的凭据没有理由旅行到那里（§5.5 把源分开） | 一个 GitHub 凭据会被泄露给两个第三方 |
| 2.5 | token **从不打印、从不回显、从不进 URL**，缺失时行为完全不变 | 它只被 `request_headers` 读取，只做一件事：加一个请求头 | 凭据进入 stdout/stderr/日志（有回归测试盯着） |
| 2.6 | 认证与否**从 API 自己报的 limit 读**（10 = 匿名，30 = 带 token），不读环境 | 报告的是**实际发出去的**请求状态，不是环境声称的状态 | health 会在 token 其实没生效时显示"已认证" |

## 3. 检索词的形状

| # | 决策 | 理由 | 代价（若判断错了） |
|---|---|---|---|
| 3.1 ★ | **一次请求只携带一个概念名词；不用引号、不用括号 OR**；多词则空格连接（GitHub 按 AND 处理） | 实测：引号把单词 `test selection` 从 11 条打到 1 条、把引号对打到 **0 条**——0 会触发静默跳过，是本项目最严重的失败；括号 OR 在**通用名词**上退化成 11108 条近义噪声 | 召回崩塌且**以"确实没有"的形式**表现出来（本项目存在的理由就是消除这一格）。注意：括号 OR 在**具体词**上确实有效（`markdown viewer OR terminal markdown` → 130 条、glow 第 2），所以规则是"一次一名词"，不是"永不用 OR" |
| 3.2 | 重试阶梯的**第一步是换概念名词**，然后才是去 `pushed:`、去 `stars:`、纯关键词 | 实测：`test impact analysis` 强过滤全灭，而 `test selection` 命中 526★ 在位者——换词比放宽阈值有效得多 | 真实答案被强过滤漏掉，而调用方以为自己已经"放宽过了" |
| 3.3 | L1 下 `probe.py search` **一次调用内**自动走完降过滤的三档 | 少一次往返、少花一次配额；调用方只需要重复"换词"这一步 | 默认**不加** `--strict`：它只跑强过滤那一档，等于关掉降过滤重试层 |
| 3.4 | 中文需求**必须先转成英文**概念名词（`references/query-patterns.md`，用例 c10 专门测这条） | 中文查询在 GitHub 上等于没查：中文写的仓库名/描述占比极低 | 全中文检索 → 0 命中 → 被误判成"确实没有"而静默跳过 |

## 4. 失败语义（本项目最不能让步的一组）

| # | 决策 | 理由 | 代价（若判断错了） |
|---|---|---|---|
| 4.1 ★ | **`network` 与 `timeout` 是两个不同的 `reason`** | §6 给它们的补救不同（查网络 vs 稍后重试）；把 DNS 失败报成"超时"会把人指到错误的修法上 | 用户按错误的原因去修一个没坏的东西 |
| 4.2 ★ | **非传输类的 4xx（404/400/422…）→ `reason: null`**，不借 `timeout` | 请求**已送达并被拒绝**，这不是传输状况；`reason` 的语义是"调用方能据以行动的原因" | 把"这个名字不存在"报成"网络超时"（§13.4、§13.5） |
| 4.3 ★ | **内部错误 → `degraded` + `reason: null` + stderr 一行诊断** | 真实的 cause 是 bug 或读不懂的响应体时，报一个传输层原因就是**编造原因**——在"绝不假装"的契约里比"没有原因"更糟 | 只读机器字段的消费者看到 `degraded` 却没有原因字符串；人看 stderr |
| 4.4 ★ | **`reason` 保留给"整个操作失败"**；补充源失败只把它自己那条 `status` 标成 `failed`，信封保持 `ok`、`reason` 保持 `null` | 一次补充源没应答不代表这次检索作废（GitHub 已经作答） | 部分失败不够显眼——所以配了下面 4.5 |
| 4.5 ★ | **补充源失败必须写一行 stderr**（spec v2.2） | HN 只在 GitHub 返回空时才被查询，所以它的失败**100%** 落在 §4.3 声明为"真的没有"的那个信封上（`ok` + `[]`）；stdout 已经用满（`reason` 归整个操作），stderr 是唯一剩下的人读通道 | 静默：调用方把一个挂掉的 HN 读成"确实没有先例"——正是 Testrim 那一幕 |
| 4.6 ★ | **调用方必须检查 `any(sources[i].status != "ok")`**，任何非 ok 的源都算"这次没查全" | 同上：形状一样，只有源列表能区分 | 决策表第 1 行失效，回到 4.5 的失败 |
| 4.7 ★ | **`--source X` 而 X 没有检索器 → 整体降级（退出码 2）**，绝不悄悄换成 GitHub 的数据 | 拿 GitHub 的数据回答 `--source hn` 会直接污染 eval（"只有 HN 命中"那条用例），把"不是这个源"伪装成"查过了" | 错误方向在这里必须是安全的那一侧：宁可显式失败，不可静默给错数据 |
| 4.8 | **`--source X`（X 有检索器）失败 → 整体降级**，而 `auto` 下补充源失败只是部分失败 | 显式请求单一源而它失败 = 整个操作失败；主力已作答时补充源失败 = 部分失败 | 一个分支 + 一个测试；两种失败的可见性会混淆 |
| 4.9 ★ | **含义不明的响应体降级，不被读成"0 结果"**（`_github_page` / `_repo_page` / `_hn_page` / `_hf_models`） | 一个读不懂的 200 与"确实没有"必须是两个信封；真正的 `{"total_count": 0, "items": []}` 仍然走 `ok` + `[]` | 坏掉的 API 回答变成权威的"没有先例" |
| 4.10 ★ | **HN 的 `_hn_hits` 也走 `_hn_page`**（终审 Critical，本轮修复） | 原先 `data.get("hits") or []` 把没有 `hits` 的 200 平滑成"HN 答了、0 条"，而 `health` 对**同一个 body** 报 failed——工具自相矛盾，且矛盾的那一侧正好是权威的"真的没有"形状 | 每一个 HN 失败都落在最危险的信封上且无 stderr；现在它抛错 → 分类 → 补充源标 failed + stderr |
| 4.11 | **`health` 必须返回非零并逐源报告**，绝不"打印点什么然后退出 0" | §6 指派 `health` 就是发现死网络的那一阶段；一个永远退出 0 的 health 无法区分"网通"和"网死" | 死网络一路走到用户面前才被发现 |
| 4.12 | `health` **不认证一个它读不懂的 body**（HN/HF 用检索器自己的形状检查） | health 报 ok 会让调用方去用一个连一次请求都服务不了的源 | health 说健康、检索随即失败（两个阶段互相矛盾） |
| 4.13 | `health` 读 `/rate_limit`，**不花**一次搜索配额；`core` 桶只报告、不单独翻判决 | `/rate_limit` 不消耗任何桶；`core` 只限制 `repo` 补全，而一个非零 health 会把 skill 送去 L2/L3，用真实精度换一个不必要的东西 | 一次 health 花掉 10 次/分钟里的一次；或 health 因为 core 桶紧张而误报不健康 |

## 5. 源策略与字段语义

| # | 决策 | 理由 | 代价（若判断错了） |
|---|---|---|---|
| 5.1 | **只有三个源**（GitHub 主力 / HN 补充 / HF 条件），不做注册表扇出 | 实测：GitLab 公开搜索前三名均 1★、Product Hunt 无文本搜索、Sourcegraph/SO 答的是"怎么写"、npm/crates 只支持精确包名 | 广度只能来自过滤档位与检索词，不能来自源的数量（这是有意的：多源实测是噪音） |
| 5.2 ★ | **`package` 子命令不做**（有意留置） | 计划里没有任何任务认领它、§5.3 的数据流没有一步调用它，而 npm/crates 的关键词搜索实测是噪音 | 用户点名某个包时没有"一条命令查精确包"的路径；将来要加约 15 行（§13.1） |
| 5.3 | **HN 条目只带 HN 能提供的东西**（title / points / created_at / 外链），构造新字典而不是复制 hit | 借用 repo 形状的字段（stars / license / archived）等于把 HN 的热度当成仓库成熟度 | 一个 42 points 的 Show HN 会被写成"成熟项目" |
| 5.4 | **HN 的 `total` = Algolia 的 `nbHits`**，不是 `len(results)` | `hitsPerPage` 只是分页上限，匹配数由源自己报告——与 GitHub 的 `total_count` 同理 | 把"这一页返回了 8 条"写成"一共只有 8 条" |
| 5.5 ★ | **HF 的 `total` 只能是 `len(results)`**，且必须读成"Hub 返回了 N 条" | 该端点返回裸数组，根本没有匹配数可言——发明一个就是编数字 | 消费者把"返回了 N"读成"Hub 上只有 N 个"（§13.7） |
| 5.6 | **HF 是条件源**：`auto` 下只有需求含 AI/ML 语义才查；条目与代码仓库**分列**，downloads/likes **不是**成熟度 | 实测 HF 对通用需求是噪音；模型不是能直接 drop-in 的代码库 | 通用需求被塞满模型噪声；或用户把模型热度当成项目成熟度 |
| 5.7 ★ | **显式 `--source hf` 不加 AI 门槛** | §5.5 的"人工强制单源"优先于 brief 的措辞；给一个强制单源加门槛，调用方只会拿到 `ok`+`[]` 或一个降级 | 明确要求查 HF 的人得到一个"查过了，没有"的假象 |
| 5.8 | `--source hn` 时忽略 `--strict`，tier 恒为 `plain` | HN 没有过滤阶梯；`--strict` 是 GitHub 的概念 | 一个不存在的档位被写进信源条目 |
| 5.9 | HN 与 GitHub 共用这次检索的**一次**重试预算 | 预算是"每次检索"的，不是"每个源"的 | 最坏情况下多一次 keyless 请求 |
| 5.10 | **`archived` 由 `bool()` 归一**，缺失即 `False`；`pushed_at` 缺失则是 `None`（本轮修正） | `archived` 是布尔旗标，GitHub 对仓库 payload 总会给出；而 `""` 是一个模型可以当成事实复述的**值**，`None` 才是"这里没有东西"（与其它缺失字段一致） | 清单里出现一个空的"最后一次推送"格；已同步更新依赖 `""` 的测试 |
| 5.11 | **`pushed_at` 是最后一次 push，不是最后一次提交**（措辞修正） | 打 tag 或推一条旧分支都会把它推后，所以它只能说明"最近还被人动过" | 用户以为某个归档仓库还在活跃开发 |

## 6. 契约层（SKILL.md / references）

| # | 决策 | 理由 | 代价（若判断错了） |
|---|---|---|---|
| 6.1 ★ | **交接止于 a/b 收束行**：终态 A / A2 的本轮产出 = 清单 + 建议行 + 收束行，"立刻继续原任务"**只属于终态 B** | GREEN c2 实测缺陷：清单、证据、a/b 全都对了，然后**又造了约 1280 行 `tmd.py` 加 113 个测试**——skill 当时禁止"改用户代码/装依赖"，却没有任何位置声明"本轮到此为止" | 用户还没选 a 还是 b，agent 已经替他把 b 做完了。用**结构化槽位**（必填的收束行）堵，而不是加一条禁令 |
| 6.2 | 终态是**四种**：A（有对口）/ A2（有对口但某源没查成）/ B（确实没有）/ C（检索失败） | 四种情形的措辞与"还能不能继续"各不相同；A2 正是"补充源失败"这一格 | 少一种就会把 A2 挤进 A 或 B，而这两种的处理方式相反 |
| 6.3 ★ | **"确实没有"时的静默是一句话，不是零输出** | RED 实测：基线 agent 把"没找到"变成了反问用户（c5 问"给谁用"、c6 问澄清问题）——"零输出"在真实宿主里会退化成"用提问代替结论" | 一句话的固定措辞让这一格可观察、可判定（静默正确率有观测对象）；严格照 spec 字面实现的人会看到一行字（§13.8） |
| 6.4 | 判定"是不是同一问题"要过**用途形态**与**主用途测试**，不只比交付形态 | GREEN c2 把 `patat`（终端讲稿放映器）列进了阅读器清单——介质和输入格式都对得上，主用途不同 | 清单里出现"同类不同问题"的候选；收紧的是规则，不是把 `patat` 拉黑（需求若是"在终端里做演示"，它才是命中） |
| 6.5 | 决策表**顺序不可换**：先看 `any(sources[i].status != "ok")`，再看 `status`，最后才看有没有对口条目 | 补充源失败时信封恰好长成"真的没有"的形状，顺序换了就等于把 4.5 的防线拆掉 | 一个挂掉的源被读成"确实没有先例" |
| 6.6 | **`health` 不是检索结果**（`references/query-patterns.md` 新增一行） | 它的信封也长成 `ok` + `results: []`，但那是"没有检索过"，不是"检索过、没有先例" | 调用方拿一次探活当成一次先例检索的结论 |
| 6.7 | 反规避表**只写实测出现过的说法** | 假设出来的说法就是 padding；本批没有出现新的"明知故犯"型话术（c2 不是规则违背，c3 的越预算已自述，c1 的生态问题不是规避） | 表变长而无效；若 c2 重跑出现"把收束行谈判掉"的原话，那句才是下一行的合法素材 |
| 6.8 | **不加 Stop-and-Ask 第 5 条**（针对"候选全是生态绑定、而需求是通用的"） | c1 处理得对：照常出清单、把生态差异写进建议行，没有改成提问；"某个用例通过了"不构成加规则的理由 | 加第 5 条会重新打开 RED 的失败模式（用澄清问题代替结论） |
| 6.9 | **不为 c3 的越预算加规则** | "≤3 次检索、≤45 秒"是当时的既有明文，而 c3 是**带披露**的越界——披露本身正是 skill 要的透明度 | 计数口径当年含糊；**优化回合 O.1 已把单位定为 `probe.py search` 调用次数，并写明 `health` / `repo` 不占这个次数**（本条只保留"不加规则"这个决定） |

## 7. 证据与过程
