# wheel-check：动手前先查开源先例

## 概览

**核心原则：查不查由本 skill 决定，不由请求的措辞决定；清单里的每个数字都必须来自本次真实检索。**

用户要新建一样东西、而代码还没开始写时：真的检索一次开源社区 —— 有**真正解决同一问题**的项目，就给出结构化清单并让用户选 a/b（**本轮到 a/b 为止**，动手在用户选定之后）；确实没有，就回一句"未发现可直接复用的开源方案。"然后立刻继续原任务；检索没成功，就出声说清原因。

**永不阻断用户的工作，永不替用户决定 a/b，永不编造 stars / 日期 / license。**

## 何时使用 / 何时不使用

| 触发（必须查一次） | 不触发（照常做原任务，不做任何检索） |
|---|---|
| 用户说要**新建**：项目、仓库、skill、plugin、子系统、工具、目录树 | 修 bug、排查故障 |
| "我想做一个 X" / "帮我写个 X"（X 还不存在） | 重构、改现有代码、给现有项目加依赖或换库 |
| 进入 plan mode 规划一件新东西 | 纯知识提问、让我解释概念 |
| 用户显式要求："先查一下有没有现成的" | 用户已声明跳过先例检索（本次会话内不再触发） |

边界：只对"有没有先例"发言。不评估用户该不该做，不替用户选 a/b，不自动改代码或装依赖。同一次"新建"只查一次；用户已选 a 或 b 之后不再重复检索。

## 流程：三步

### 第一步 · 提炼检索词

把需求抽象成 2–3 个英文**概念名词**（每个 1–2 个词）。中文需求必须先转成英文——中文查询在 GitHub 上等于没查。规则、实测反例与中→英映射见 `references/query-patterns.md`。

**提问只发生在两处**：第一步提炼术语时（下面的 Stop-and-Ask 第 1、4 条），和判定候选时（第 2、3 条）。其余一律**先检索、先出结论**：不要用澄清问题代替检索，也不要在检索前先确认需求和实现细节。

### 第二步 · 检索（能力阶梯，逐级降级）

| 层 | 手段 | 生效条件 | 数字可信度 |
|---|---|---|---|
| **L1** | 本 skill 自带的 `scripts/probe.py`（解释器按 `python` → `py` → `python3` 探测；参数见 `--help`） | 宿主有 shell 且解释器可用 | **完全可信** |
| **L2** | 宿主原生 HTTP 工具直接取 `api.github.com` | L1 不可用 | 可信（编排由你自己承担） |
| **L3** | 宿主 `web_search` / `web_fetch` 查网页 | L1、L2 都不可用 | **不可信——star / 日期必须标"未核实"** |

- 能用 L1 就用 L1，不能用才退 L2，都不能用才退 L3。**降级必须让用户看到**（写在清单或说明的前一行），绝不静默降级。
- 预算：≤3 次检索、总耗时 ≤45 秒。预算耗尽就用现有证据出结论并标明"未查全"——绝不因为超预算就说"没有先例"。

### 第三步 · 读返回，决定说什么

调用返回一个 JSON 信封：`status` / `reason` / `sources[]` / `results[]`。

**快速参考：按下面的顺序判断，顺序不可换**（补充源失败时，信封恰好长成"真的没有"的形状）：

| 顺序 | 观察到的形状 | 说什么 |
|---|---|---|
| 1 | 任一 `sources[i].status` 不是 `"ok"` | **出声**：这次没查全——说出是哪个源没有应答。工具给了原因（信封的 `reason`，或 stderr 上的诊断）就一并说；没给就不猜。没有对口条目时尤其不能静默："没查全"和"确实没有"是两件事。 |
| 2 | 信封 `status` 是 `"degraded"` | **出声**：报出 `reason`（并说明是哪个源失败）；`rate-limited` 时提示设置 `GITHUB_TOKEN` 或稍后重试。 |
| 3 | 全部源 `ok`，但 `results` 里没有"真正解决同一问题"的条目（含 `results: []` 与"命中全是噪音"，且重试链已走完——见 `references/query-patterns.md`） | **静默**：只回一句"未发现可直接复用的开源方案。"然后立刻继续原任务。 |
| 4 | 全部源 `ok`，且有对口条目 | **出声**：五字段结构化清单 + 证据 + a/b 询问，回话以**收束行**结束（见下）。 |

第 3、4 行都要求先判定"是不是同一问题"——标准见 `references/triage-rubric.md`；**共享领域不算同一问题**。四种终态的成稿措辞见 `references/verdicts.md`。

### 结构化清单（五字段 + 证据 + 选择）

必含五字段：**项目名称 / 核心功能 / 可复用点 / 与本方案的差异 / 潜在风险**。每个候选附证据：stars、最后提交、license、archived、链接。建议行给出 a/b 并请用户选择，回话以**收束行**结束（见下）。完整模板见 `references/verdicts.md`。

- 证据只能来自本次返回。工具没给的字段就不写，绝不估、绝不回忆。
- L3 拿到的 star / 日期一律标"**未核实**"。
- `kind: "discussion"`（HN）条目**没有** stars / license：要推荐它外链的仓库，先补全该仓库自己的硬事实；补不到就在该行标"证据不全（HN 命中，未核实仓库）"。**不得把 HN 的 points / 热度当作仓库成熟度。**
- `kind: "model"`（HF）是模型，不是可以直接拿来用的代码库：与仓库**分列**（单独一段或单独一列，注明需下载 / 微调 / 推理）。downloads 与 likes 是模型热度，不是项目成熟度。
- `total` 是该源自己报告的匹配数，不是"世界上有这么多"；HF 的 `total` 只表示"Hub 返回了 N 条"。
- **交回形状（终态 A / A2 的收束）**：本轮 = 清单 + 建议行 + **收束行**；收束行是回话的最后一行（模板与措辞见 `references/verdicts.md`），写明本轮产出就是上面这份清单、动手发生在用户选定 a 或 b 之后。**"立刻继续原任务"只属于终态 B**：没有先例时没有可选项要等；有对口条目时，原任务等用户选完 a/b 再开工。

### Stop-and-Ask（四情形，必须停下来问）

1. 需求存在多种等价术语、会显著改变检索结果，而你无法排序；
2. 某候选落在"是否真正解决同一问题"的边界上，而这个判断会改变 a/b 的建议；
3. ≥2 个候选都声称解决同一问题，且推荐哪个会实质影响用户的复用决策；
4. 用户的需求描述不足以提炼出任何技术术语（例：只给了产品名）。

提问格式：**具体问题 + 可选项 + 我的建议**，等确认后再继续。除这四种情形，不要用提问代替检索、也不要用提问代替结论。

## 常见错误与反规避

| 做法 / 说法 | 事实 |
|---|---|
| 用中文词去查 GitHub | 等于没查。中文需求先转成 2–3 个英文概念名词。 |
| 一次请求塞进"改完文件只跑受影响的测试"这种长句 | 多词长短语杀光召回：实测 `test impact analysis` → 3 条垃圾，而 `test selection` → 命中 526★ 在位者。一次只发一个概念名词。 |
| 只查一个词，返回空就说"没有先例" | 空可能是强过滤漏了。先换概念名词重试，再看补充源，最后才可能下"没有"的结论。 |
| 「先问清楚用户/需求细节，再决定查什么」 | RED 实测：这条把本该静默的场景变成了反问。除 Stop-and-Ask 四种情形外，先检索、先出结论。 |
| 「这个需求看起来不用查，我心里有数」 | RED 实测：查不查完全取决于当时怎么读请求——本 skill 存在的意义就是去掉这份随机性。触发清单命中就查一次。 |
| 「我对这个领域很熟，直接列项目名就行」 | 记忆里的 star / license / 最后提交都会过期。本 skill 的数字必须来自本次检索。 |
| 「清单里有项目名和定性分析就够了，用户自己能去看 star」 | 用户要据此决定复用还是自研；没有硬事实就没有决策依据。 |
| 「工具报错了，但我大概知道结果，就按'没找到'继续」 | 这正是本项目要消除的混淆：`degraded`、以及任何 `sources[i].status != "ok"`，都必须出声。"没查成"永远不等于"没有"。 |
| 「HN 有 42 points，说明这个项目挺成熟」 | HN 只有标题、热度和外链。成熟度必须来自仓库硬事实——要么补全，要么标"证据不全"。 |

（本表只写实测出现过的做法；没有实测到的说法不预先罗列。）
