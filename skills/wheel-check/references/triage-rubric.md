# triage-rubric —— 什么算"真正解决同一问题"

给 `wheel-check` 的判定层用：检索回来的条目**由你**判定相关性（数据层不做语义判断，只回硬事实与过滤档位）。

## 判定三条件（同时成立才算命中）

1. **同一个问题**：把需求写成"输入 → 输出 → 使用形态"，候选必须能对上同样的输入与输出。
2. **同一种使用形态**：交付形态（CLI / 命令、钩子、库、服务、插件、平台）与**用途形态**（读、讲、生成、编排……）都要对得上 —— 任一个不同就是不同的东西。
3. **是成品，不是原材料**：装上或接上就能解决用户这件事。需要用户自己写编排、自己搭一套系统的引擎 / 框架 / 能力库，不算"别人已经做完了"。

**主用途测试（把上面三条落到一句话的判断）**：把候选代进需求句——「用它来做 <用户要做的这件事>」。这句话**不改写它的主用途**就成立，才算命中；必须换一种用法才成立（当幻灯片讲、当引擎嵌、当平台部署、当能力库调用）的，是**不同的问题**，不列进清单。

**共享领域不算同一问题。** 同在"测试""照片""审批"领域不构成命中。实测反例：

| 检索命中 | 为什么不是同一问题 |
|---|---|
| `tcgoetz/GarminDB`（`file watcher` 关键词命中，曾排到第 2） | 它是 Garmin 运动数据同步工具，与"监视文件变化"只是共享词面 |
| `patat`（面对"在终端里读 markdown"，GREEN c2 里被列进了阅读器清单） | **终端讲稿放映**工具（Terminal-based presentations using Pandoc）：介质和输入格式都对得上，主用途却是把 markdown 当幻灯片**讲**，不是当文档**读**。需求若是"在终端里做幻灯片"，它才是命中 |
| `Immich` / `PhotoPrism` / `digiKam`（面对"把我这台机器上某年的照片按人脸分组归档"） | 自建相册**平台**：要用户换掉整套照片使用形态；用户要的是一次性脚本 |
| `face_recognition` / `insightface` / OpenCV YuNet+SFace（同一需求） | **原材料**：只提供人脸识别能力，扫描目录、按人分组、归档这些编排仍要用户自己写 |
| `Flowable` / `Camunda`（工作流引擎）、`O2OA`（整套 OA 平台）（面对"把我们公司内部的报销审批流程搬到网页上"） | 前者是用户仍要开发的引擎，后者要用户换掉整个办公形态；都不是"这件事已经有人做完了" |

反过来，`charmbracelet/glow`（终端 markdown 阅读器）、`mdcat`（`cat` 的 markdown 版）、`gitleaks`（提交前扫密钥这一类成品）、`Tinder/bazel-diff`、`pytest-testmon`（受影响的测试选择）都是**同一形态的成品**，算命中。

## 成熟度证据字段

每个候选都要给。**字段来源只有两个：本次检索的返回，或"未核实"三个字。**

| 字段 | 说明 | 拿不到时 |
|---|---|---|
| stars | 仓库硬事实 | 不写。L3 场景写"未核实" |
| 最后提交 | 仓库硬事实（是否还在维护） | 不写。L3 场景写"未核实" |
| license | 仓库自己的声明（不要转述二手说法） | 不写"应该是 MIT"这类猜测 |
| archived | `true` 必须写明——这是复用决策的关键风险 | — |
| 链接 | 总是给 | — |

**成熟度不是相关性门槛。** 相关性由上面的三条件判定；stars 少、项目新，都不构成删掉一个对口候选的理由（这正是强过滤会漏掉真答案的原因）。成熟度只进"证据"与"潜在风险"两处。

## 证据随条目的 `kind` 而不同

- **`kind: "repo"`**：stars / pushed_at / license / archived / language / description，字段齐全。
- **`kind: "discussion"`（HN）**：只有 title / points / created_at / external_url，**没有** stars、没有 license。
  - 若外链指向一个你要推荐给用户的仓库 → 先补全该仓库自己的硬事实。
  - 补不到 → 该行标 **"证据不全（HN 命中，未核实仓库）"**。
  - **禁止把 points / 热度当作仓库成熟度**，也不要在证据列里把它和 stars 并列。
- **`kind: "model"`（HF）**：只有 model_id / downloads / likes。
  - 模型**不是**可以直接 drop-in 的代码库：与仓库分列（单独一段或单独一列），并注明它是需要下载 / 微调 / 推理的产物。
  - downloads / likes 是模型热度，不是项目成熟度。

## `total` 怎么读

- GitHub / HN 的 `total` 是**该源自己报告的匹配数**，可能大于你看到的条目数（一页只返回 `limit` 条）。它只说明"这次查询匹配了多少"，不说明"世界上有这么多"。
- **HF 是例外**：Hub 的模型接口不提供匹配总数，`total` 只表示 **"Hub 返回了 N 条"**。不得读成"Hub 上只有 N 个"，也不得写成"共 N 个模型"。

## 明确排除（命中也不要列进清单）

| 排除 | 原因 |
|---|---|
| 专利检索 / 专利分析类工具 | 关键词 `prior art` 会大量命中它们；本 skill 找的是**开源实现**，不是专利 |
| 代码抄袭检测 / 代码相似度扫描类工具 | 与"先例发现"是不同的东西 |
| npm / crates.io 的关键词搜索结果 | 实测只支持精确包名，关键词搜索是噪音（用户点名包名时才用精确查询） |
| 需要用户换掉整个工作形态才能用的东西（自建平台替换现有工具链） | 属于"与本方案的差异 / 潜在风险"，不是同一问题的解 |

## 辅助清单：常见"重复造轮子"高危区

登录鉴权、日期时间处理、表单校验、CLI 参数解析、重试与退避、限流、日志聚合、序列化、状态机、任务调度、缓存、分页、图片处理、markdown 渲染、密钥扫描、受影响测试选择。

这张表只说明"这类需求值得查一次"，**不构成判定**——判定仍然走上面的三条件。
