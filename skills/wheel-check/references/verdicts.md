# verdicts —— 四种终态的措辞模板（A / A2 / B / C）

选哪一种终态，由 `SKILL.md` 第三步的顺序表决定（先看 `sources[i].status`，再看 `status`，最后看有没有对口条目）。下面是成稿措辞，形状照抄即可。

## 终态 A：有对口条目 → 结构化清单 + a/b 询问

````markdown
### 开源先例：<一句话需求>

| 项目 | 核心功能 | 可复用点 | 与本方案的差异 | 潜在风险 | 证据 |
|---|---|---|---|---|---|
| owner/name | <它做什么> | <能直接拿来用的部分> | <和你方案不同的地方> | <archived / 许可证 / 维护状态 / 形态差异等> | <stars>★ · <最后一次推送> · <license> |

**建议**：a) 沿用上面 N 个项目继续开发（可复用 X、需改造 Y） / b) 不沿用，纯自研
请选择 a 或 b。本轮产出到这份清单为止；你选定 a 或 b 之后我再动手。
````

- 五字段（项目名称 / 核心功能 / 可复用点 / 与本方案的差异 / 潜在风险）与证据列**一个都不能少**。
- **收束行（必填）**：回话的最后一行，形状是"本轮产出到这份清单为止；你选定 a 或 b 之后我再动手"。这一轮从检索开始、到收束行结束：清单之后不再有任何产物——实现、脚手架、原型、示例代码、依赖安装都属于**用户选定 a 或 b 之后**的那个回合。
- 与终态 B 的分界：**"立刻继续原任务"只属于终态 B**（确实没有先例，就没有可选项要等）；终态 A / A2 的"继续"要等用户选定 a 或 b，那一轮才轮到交回主模型继续原任务。
- 证据列的格式是 `<stars>★ · <最后一次推送> · <license>`（"最后一次推送"就是 `pushed_at`：它是**最后一次 push**，不是最后一次提交——打 tag 或推一条旧分支都会把它推后，所以它只能说明"这个仓库最近还被人动过"）—— **格式可以照抄，数字必须来自本次检索返回**；`archived: true` 写在"潜在风险"里。
- L3 场景：证据列写成 `<stars>★（未核实） · <最后一次推送>（未核实）`，并在清单前加一行说明。
- HN 的 `kind: "discussion"` 条目：补全了仓库硬事实就按仓库行写；补不到就写 `证据不全（HN 命中，未核实仓库）`，**不要**把 points 放进证据列。
- HF 的 `kind: "model"` 条目：单独一段或单独一列，注明"模型，需下载 / 微调 / 推理"，不与仓库混排。
- 建议行只写事实依据（能复用什么、要改造什么），**不要写"我认为你应该选 a"**——选择权在用户。
- 清单是**供料**：它是给用户做决定的输入；交回主模型接着做原任务，发生在**用户选定 a 或 b 之后**（见收束行）。

### a/b 选项的措辞来源

用决策矩阵的四档来写"可复用点 / 与本方案的差异"两列，让 a 与 b 各自的代价一眼可见：

| 档位 | 落在哪一列 |
|---|---|
| Adopt 直接采用 | "可复用点"：整个项目直接可用 |
| Extend 扩展 | "可复用点" + "差异"：拿它当底座，改一部分、加一部分 |
| Compose 组合 | 多个候选各覆盖一部分，需要拼起来 |
| Build 自研 | b 选项：上面都不成立时纯自研 |

这是**措辞来源**，不是评分：不要在清单里另开一列写 adopt/adapt 之类的标签，也不要给候选打分或排序（本 skill 只给事实与判定）。

## 终态 A2：有对口条目，但某个源没查成

清单照终态 A 给，然后在清单后补一行——不改变清单本身：

````markdown
> 说明：这次只覆盖了 <可用源>；<失败源> 没有应答（<原因>），所以上面的结果不是全部。
````

- 说明行插在收束行之前，清单本身不改；**收束行仍是回话的最后一行**（内容同终态 A：本轮产出到这份清单为止，用户选定 a 或 b 之后才动手）。

## 终态 B：全部源 `ok`，但没有对口条目 → 一句话静默

```
未发现可直接复用的开源方案。
```

然后**立刻继续原任务**（同一个回合里接着做用户原本要你做的事）。**只有终态 B 这样继续**：确实没有先例，就没有可选项要等；终态 A / A2 要先等用户选定 a 或 b。此外不输出任何东西：

- 不提问、不请用户确认、不要求用户补充信息；
- 不列近似但不相关的候选（"有几个相关的你可以看看…"不是静默）；
- 不报告查了哪些词、查了哪些源、查了几次；
- 不写"我没找到，你要不要我换个词再查"。

## 终态 C：检索失败 → 出声报原因

````markdown
先例检索没成功（<reason>），这次不能当作"没有先例"。
````

`reason` 翻成用户能懂的话，并给出可行动作：

| `reason` / 情况 | 说法 + 动作 |
|---|---|
| `rate-limited` | GitHub 搜索配额用完了（未认证 10 次/分钟）。可设置 `GITHUB_TOKEN` 提高配额后重试，或稍后再查。 |
| `network` | 网络不通（DNS / 连接被拒 / 代理）。修好网络后重试，或降级到宿主 HTTP / 网页检索继续查。 |
| `timeout` | 请求超时。稍后重试。 |
| `null` | 工具内部错误或返回体读不出来（细节在 stderr）。**这不是"没有先例"。** |
| 显式指定的单源失败 | 说明是哪个源失败、为什么；不要拿别的源的数据顶替。 |

信封**仍是 `ok`**、但某个源 `status != "ok"` 时（典型的 HN / HF 补充源失败——这种形状和"真的没有"长得一模一样，最容易读错）：

````markdown
这次先例检索没查全：<失败源> 没有应答，所以现在不能说"没有现成的"。
````

源条目里只有 `source` 和 `status`，**没有**原因字段——原因（若有）在 stderr 上。拿到就说，拿不到就只说"没有应答"，不要替它编一个原因。

任何一种失败都要说清"这次没查成"，**绝不把它写成"查过了，没有"**。预算耗尽（≤45 秒 / ≤3 次 `probe.py search` 调用）时同样按这里处理：用现有证据出结论并标明未查全。

## 通用措辞规则

- 任何数字都必须能在本次返回里找到出处；找不到就写"未核实"或不写。
- 降级（L2 / L3）必须写在用户看得到的地方，不静默降级。
- 不要在回话里暴露工具细节（原始 JSON、参数、stderr 原文）——只说结论与原因。
